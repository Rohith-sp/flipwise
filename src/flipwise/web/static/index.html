01 · Overview

Run ML jobs where and when the grid is cleaner, without re-planning all the time

A global scheduler receives GPU jobs and places each one at one of three Indian datacentres (Delhi NCR, Mumbai, Chennai) and a start time up to 24 h later, using carbon-intensity forecasts. Forecasts keep changing, so a plan that was best an hour ago may not be best now. The research question: when is it worth re-planning a waiting job? Decision-flip is our answer: a cheap screen that skips re-planning when it provably cannot pay off, and a noise margin that ignores gains smaller than the forecast's own uncertainty.

What decision-flip buys

Against fixed_savings, which re-scores every waiting job at every forecast update and moves it when the gain clears a threshold, decision-flip reaches statistically the same emissions with a fraction of the planner work and far fewer plan changes. Fewer plan changes mean fewer data transfers, fewer lost queue positions, and users who can predict where their job runs.

What it does not do

No policy saves energy. Every policy runs exactly the same jobs for the same time, so energy is identical (see the Results table). What changes is when and where that energy is drawn, and so how much CO₂ it carries.

The carbon prize itself is modest on Indian grids: the three regions are coal-heavy and share a national daily shape, so even a perfect-information oracle (pig) only gets a few percent below carbon-blind scheduling. Decision-flip's case is efficiency and stability at the same carbon, and that case gets stronger as the number of datacentres and jobs grows (section 06).

02 · How it works

Two schedulers, one information boundary

The global scheduler (our work) decides which datacentre and which release time. Each datacentre's local scheduler then decides which queued job starts next on its GPUs. The global scheduler sees only forecasts and estimates; the real carbon and real runtimes are hidden from it and used only to score the outcome.

Life of one job

Your questions, answered

Does the local scheduler matter? Is it FCFS?

It is not FCFS. It is a FIFO queue with first-fit dispatch: every time something changes, it walks the queue front to back and starts every job that fits in the free GPUs/CPUs/memory. A small job can therefore start ahead of a big job that is blocked. There is no reservation, so a very large job can wait while small ones keep slipping past (a known weakness; EASY backfilling would fix it).

For the research result it matters little: all seven policies share the same local scheduler, so it cannot explain differences between them. For a real product it matters a lot, but you would not write it: Slurm or Kubernetes already is the local scheduler, and Flipwise would sit in front of them.

Real processes or separate databases?

Real processes. A datacentre here is not storage; it is an actor that owns a queue and decides what starts. Separate databases would only model its state, not its behaviour. Flipwise already has this: flipwise dc-serve runs one datacentre as an HTTP service, and the coordinator talks to it through the same DatacentreClient interface. Requirement R-DEP-1 checks that results are byte-identical to the in-process run.

In the Live arena, choose Datacentres: real processes. The backend starts 3 dc-serve processes per scheduler, and each datacentre panel shows its PID, port, request count and latency. Separate terminals add nothing beyond theatre: the process list is the proof.

03 · Decision-flip

Re-plan only when the answer could actually flip

At every forecast update each waiting job has an incumbent plan with estimated emissions Ŝa. Re-scoring it means evaluating every datacentre × every 30-minute start slot in the next 24 h, including queue projections: expensive, and mostly pointless. Decision-flip puts two checks in front of a move.

Try one decision

Values in kg CO₂ for one job. Defaults are typical of the test runs.

The rules

gmin = max(gabs, grel·Ŝa) + κswitch + κqueue + λovh

The benefit gate: the least a move must save to be worth it. Frozen on validation data: grel = 0.05 (decision-flip), 0.01 (fixed_savings); κ and λ are 0 in the current runs (moves are free; see Limits).

Stage 1 · skip if Ŝa − LB < gmin

LB = the cheapest emissions any alternative could reach: the cleanest forecast window of the job's runtime at any datacentre before its deadline, ignoring queues. If even that cannot clear the gate, no real alternative can, so the full re-score is skipped. This is provably safe: at θ = 0, decision-flip makes exactly the decisions of fixed_savings with the same gate (property P1, checked on real data).

Stage 2 · move if Ŝa − Ŝb ≥ gmin + θ·wab and the gain is > 0

wab = the paired uncertainty of the comparison: forecast-error quantiles over each option's wait range, plus runtime uncertainty. θ = 0.1. If the interval is malformed or wider than wmax = 2 × Ŝa, the margin is switched off (θeff = 0) rather than blocking every move.

Throttles shared by all re-planners: cooldown 1,800 s per job, at most 3 moves per job.

06 · At scale

What happens with more datacentres

A global router for a company would sit in front of many datacentres, not three. We grow the federation from 3 to 12 datacentres and grow the job load with it, so every datacentre stays about as busy as before. Every full re-score must then evaluate more datacentres × slots for more waiting jobs.

07 · The data

Real jobs, real Indian grids, real forecast errors

Nothing is synthetic except the combination. Jobs come from Alibaba's production GPU cluster trace; carbon truth is built from Grid-India generation by fuel and CEA emission factors; forecast errors are real errors of the GB national forecaster (NESO), scaled onto Indian truth because India publishes no regional carbon forecast.

08 · Limits & next steps

What this does not show yet

Moves are free in the model

κswitch and κqueue are 0, so re-planning costs nothing in the results. In reality a move can mean shipping datasets between regions and losing a queue position. Giving moves a realistic cost should hurt the policies that move most, and it is the experiment most likely to separate decision-flip from fixed_savings on carbon too.

The carbon prize is small here

The three grids are all coal-heavy and share one national within-day shape (Grid-India publishes only daily regional fuel mixes), so they move together. Even the oracle gets only a few percent. A grid that differs (solar-heavy Rajasthan or Karnataka, or a hydro-rich region) would test spatial shifting properly.

Power values are placeholders

Blocker B3: 0.3 kW per GPU and 0.01 kW per CPU core, PUE 1. Treat kg CO₂ as relative between policies, not as an absolute footprint.

From simulator to product

The sound first product is not a live router. It is the simulator as a savings estimator run on a company's own job logs, then an advisory plugin for an existing multi-cluster layer (Kueue MultiKueue, Karmada, Slurm federation) that recommends a placement. Real-time forecasts, data gravity, and trust come before autonomy.

Next experiments

Sensitivity sweeps (θ, grel, forecast-error scale α) and ablations of the screen and the width terms on validation data; a move-cost sweep; a divergent grid; the DT3 cloud deployment.

Integrity rules the dashboard keeps

The live arena uses validation-period data (trace days 25–28, carbon week of 3 Jul 2023), never the test set. The tables are read from the saved result files. The live lanes run the unchanged simulator, so they make the same decisions as flipwise run.
